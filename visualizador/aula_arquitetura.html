📂 Por que existem include/ e src/?

.h (include/) — o "cardápio"
Só declara o que existe: o nome das funções e os parâmetros que recebem.
.cpp (src/) — a "cozinha"
Onde cada função é implementada de verdade.

O main.cpp só precisa conhecer os .h. O Makefile compila cada .cpp separadamente e depois junta (linka) tudo no executável projeto.

🧱1. Automato.h / Automato.cpp

include/Automato.h src/Automato.cpp

Responsabilidade: representar um autômato na memória. Todos os outros arquivos usam essa classe.

Como a teoria vira código

Na teoria, um autômato é a 5-upla M = (Q, Σ, δ, q₀, F). No código, cada parte vira um campo:

TeoriaCódigoTipo
Q (estados)estadosvector<Estado>
Σ (alfabeto)alfabetoset<char> (não repete e fica ordenado)
δ (transições)transicoesvector<Transicao>
q₀ (inicial)estadoInicialint (índice no vetor)
F (finais)campo final dentro de cada Estadobool
(extra) erroestadoErroint
struct Estado    { int id; string nome; bool final; vector<string> tokens; bool isErro; };
struct Transicao { int origem; char simbolo; int destino; bool epsilon; };
💡 Ideia-chave: o id de um estado é a posição dele no vetor, então estados[3] é o estado de id 3. Isso simplifica tudo: para marcar "visitado", basta um vector<bool> do mesmo tamanho.
💡 tokens é um vetor porque um estado final pode reconhecer mais de um token ao mesmo tempo (por exemplo, quando um token e uma gramática terminam no mesmo lugar).

Métodos principais

MétodoO que faz
adicionarEstado(nome)push_back no vetor; devolve o novo id (= size() antes de inserir)
marcarFinal(id, token)final = true e adiciona o token sem repetir (usa find)
adicionarTransicao(o, c, d)valida os ids, guarda a transição e insere c no alfabeto
getDestinos(o, c)percorre todas as transições e devolve todos os destinos (AFND: pode haver vários)
getDestinoAFD(o, c)devolve o primeiro destino, ou -1 se não houver (AFD: só existe um)
temTransicao(o, c)getDestinoAFD(o, c) != -1
imprimirTabela(titulo)desenha a matriz δ no console (linhas = estados, colunas = símbolos)
ℹ️ O alfabeto não é informado pelo usuário: ele vai sendo montado automaticamente conforme as transições são criadas.

📄2. LeitorArquivo.cpp — do texto para o AFND

src/LeitorArquivo.cpp

Responsabilidade: ler o .txt e montar o AFND seguindo a regra do professor: só o estado inicial é compartilhado; os demais estados são exclusivos.

📥 caminho do arquivo➜📤 AFND preenchido (por referência)

Entrada usada como exemplo (professor.txt)

se                                              ← token
entao                                           ← token
senao                                           ← token
<S> ::= a<A> | e<A> | i<A> | o<A> | u<A>          ← gramática (tem ::=)
<A> ::= a<A> | e<A> | i<A> | o<A> | u<A> | ε      ← gramática (tem ::=)

Fase A — classificar as linhas

para cada linha do arquivo:
    tira os espaços das pontas (trimString)
    se vazia, ou começa com "#" ou "//"  → ignora
    se é do tipo "[ALGO]"                 → marcador de seção (pode mudar o nome do token da GR)
    se contém "::="                       → PRODUÇÃO de gramática
                                            (separa o lado esquerdo e as alternativas pelo '|')
    senão                                 → TOKEN (vai para o vetor tokens)

Fase B — criar o estado inicial

int S = automato.adicionarEstado("S");
automato.definirEstadoInicial(S);

A classe auxiliar GeradorNomes gera os próximos nomes A, B, C… (pulando o S, que é reservado) e, quando as letras acabam, q1, q2…

Fase C — tokens (um corredor exclusivo por token)

para cada token:
    atual = S
    para cada caractere c do token:
        novo = adicionarEstado(próximo nome)   ← SEMPRE cria um estado novo
        adicionarTransicao(atual, c, novo)
        atual = novo
    marcarFinal(atual, token)

Fase D — gramática regular

estadosGR = map<string,int>              // "nome do não-terminal" → id do estado
estadosGR[ primeiro não-terminal ] = S   // o <S> da GR usa o MESMO S (compartilhado)
para cada outro não-terminal: cria um estado novo

para cada produção, para cada alternativa:
    "ε"     → marcarFinal(origem, "variavel")
    "a<A>"  → adicionarTransicao(origem, 'a', estadosGR["<A>"])
    "a"     → cria um estado final novo e adiciona origem -a-> novo
Figura 1 — AFND gerado (14 estados). Círculo duplo = final. Setas vermelhas = não-determinismo: S com s vai para A e H; S com e vai para C e M.
⚠️ Como o estado criado é sempre novo, se e senao não compartilham o caminho do s. Por isso S tem duas transições com s. É exatamente aí que nasce o não-determinismo.

🔀4. Determinizar.cpp — AFND ➜ AFD

src/Determinizar.cpp

Responsabilidade: eliminar o não-determinismo usando a construção de subconjuntos.

📥 AFND➜📤 novo AFD
🧠 A ideia em uma frase: cada estado do AFD representa um conjunto de estados do AFND, ou seja, "todos os lugares onde eu poderia estar".

Estruturas de dados (e por que cada uma)

EstruturaPara quê
set<int>representa um subconjunto. Já vem ordenado e sem repetição, então {A,H} e {H,A} viram a mesma coisa
map<set<int>, int>"esse conjunto já virou estado? Qual é o id dele?" Evita criar estados duplicados
queue<set<int>>fila dos conjuntos que ainda faltam processar (é uma BFS)

Algoritmo

D0 = fecho-ε({S}); cria o estado D0; coloca na fila
enquanto a fila não estiver vazia:
    atual = fila.pop()
    para cada símbolo c do alfabeto (a,e,i,n,o,s,t,u):
        destino = união de getDestinos(q, c) para cada q em atual
        se destino vazio → continua   // sem transição; o Erro resolve depois
        destino = fecho-ε(destino)
        se destino não está no map → cria novo estado Dn e coloca na fila
        adicionarTransicao(atual, c, destino)

Ao criar cada estado (lambda criarEstadoAFD): se algum estado do conjunto for final, o novo estado também é final e herda os tokens.

Execução real com o exemplo

AFDSubconjuntoPor quêFinal?
D0{S}ponto de partida
D1{M}S com a, i, o, u★ variavel
D2{C, M}S com e → C e M★ variavel
D3{A, H}S com s → A e H
D4{D}D2 com n
D5{B, I}D3 com e★ se
D6{E}D4 com t
D7{J}D5 com n
D8{F}D6 com a
D9{K}D7 com a
D10{G}D8 com o★ entao
D11{L}D9 com o★ senao
Figura 2 — AFD determinizado (12 estados). Embaixo de cada estado: o subconjunto do AFND que ele representa.
✅ 14 ➜ 12 estados. A partir daqui, cada par (estado, símbolo) tem no máximo um destino.
📝 fechoEpsilon usa uma pilha para seguir as transições ε. Ele está implementado por completude teórica, mas o leitor não cria transições ε: um ε na gramática apenas marca o estado como final. Então, neste projeto, o fecho sempre devolve o próprio conjunto.

🧹5. Minimizar.cpp — remover estados inúteis

src/Minimizar.cpp

Responsabilidade: minimizar sem classes de equivalência, ou seja, não junta estados equivalentes; apenas remove dois tipos de estados inúteis.

📥 AFD➜📤 novo AFD (renomeado M0, M1, …)
🏝️ Inalcançável
Não existe caminho de q₀ até ele.
Detecta com BFS para frente a partir de q₀.
💀 Morto
Dele não existe caminho até nenhum final.
Detecta com BFS reversa a partir dos finais.

Passo 1 — alcançáveis (BFS para frente)

alcancavel[q0] = true; fila = [q0]
enquanto a fila não estiver vazia:
    atual = fila.pop()
    para cada transição atual → d:
        se !alcancavel[d]: marca e coloca na fila

Passo 2 — vivos (BFS reversa)

O truque é inverter as setas: monta transicoesReversas[destino] → lista de origens. Assim, "quem consegue chegar a um final?" vira "partindo dos finais e andando para trás, quem eu alcanço?".

coloca TODOS os finais na fila, já marcados como vivos
enquanto a fila não estiver vazia:
    atual = fila.pop()
    para cada anterior em transicoesReversas[atual]:
        se !vivo[anterior]: marca e coloca na fila

Passo 3 — reconstruir

manter[i] = alcancavel[i] && (vivo[i] || i == inicial)
para cada estado mantido: cria Mk no novo autômato; mapeamento[i] = k
copia só as transições cujas DUAS pontas foram mantidas (já traduzidas pelo mapeamento)

O vetor mapeamento funciona como um "de-para": id antigo → id novo (ou -1 se foi removido).

📊 No exemplo do professor: nada é removido (12 ➜ 12) e Dn vira Mn.

🧪 Exemplo com remoção (exemplo3_inalcancavel_e_morto.txt)

inicio
fim
<S> ::= a<A> | m<M>
<A> ::= a<A> | ε
<M> ::= m<M>          ← 💀 só fica no laço do "m" e nunca chega a um final (morto)
<Z> ::= z<Z> | ε      ← 🏝️ nenhuma transição chega em Z (inalcançável)

🚫6. CompletarAutomato.cpp — o estado de erro

src/CompletarAutomato.cpp

Responsabilidade: tornar δ uma função total: toda célula da tabela passa a ter um destino.

📥 AFD& (por referência)➜📤 o mesmo objeto, agora completo
erro = adicionarEstado("Erro")         // entra como ÚLTIMO estado
definirEstadoErro(erro)
para cada estado s (exceto o Erro):
    para cada símbolo c do alfabeto:
        se !temTransicao(s, c): adicionarTransicao(s, c, erro)
para cada símbolo c: adicionarTransicao(erro, c, erro)   // laço: não tem como sair

Repare que a função recebe Automato& (por referência): ela modifica o próprio objeto em vez de devolver uma cópia.

Tabela final de transições

➜ = inicial · * = final · Erro = célula preenchida pelo completarAFD. Total: 13 estados × 8 símbolos.

❓ Por que depois da minimização? O Erro nunca alcança um estado final, ou seja, ele é morto por definição. Se fosse criado antes, a minimização o apagaria.

✅7. VerificarEstados.cpp — a "prova real"

src/VerificarEstados.cpp

Responsabilidade: auditar o AFD final e imprimir um relatório. Não altera nada (recebe const Automato&).

Ele repete as mesmas duas BFS da minimização (encontrarAlcancaveis e encontrarEstadosQueChegamAoFinal) e confirma que:

  • não há estados inalcançáveis;
  • não há estados mortos, ignorando o Erro (i != estadoErro), que é morto de propósito.
🧮 É como conferir uma conta fazendo de novo: se a minimização funcionou, esse relatório tem que dizer "Nenhum".

🕹️8. Reconhecer.cpp — simular o AFD

src/Reconhecer.cpp

Responsabilidade: dizer se uma palavra é aceita e qual token ela representa.

📥 AFD + palavra➜📤 bool + tokens + rastro
estado = inicial; rastro = nome(inicial)
para cada caractere c da palavra:
    prox = getDestinoAFD(estado, c)
    se prox == -1        → REJEITA ("sem transição": c nem está no alfabeto)
    estado = prox; acrescenta " --c--> nome" ao rastro
    se estado == Erro    → REJEITA (para na hora: do Erro não se sai)
no fim:
    se estado é final    → ACEITA e devolve estados[estado].tokens
    senão                → REJEITA ("estado não-final")
⚡ É O(n) no tamanho da palavra (fora a busca linear dentro de getDestinoAFD). Esse é o grande ganho do AFD: uma única passada, sem voltar atrás (backtracking).
EntradaCaminhoResultado
senaoM0 -s→ M3 -e→ M5 -n→ M7 -a→ M9 -o→ M11✅ senao
seM0 -s→ M3 -e→ M5✅ se
entaoM0 -e→ M2 -n→ M4 -t→ M6 -a→ M8 -o→ M10✅ entao
aeiouM0 -a→ M1 -e→ M1 -i→ M1 -o→ M1 -u→ M1✅ variavel
senM0 → M3 → M5 → M7❌ M7 não é final
stM0 -s→ M3 -t→ Erro❌ caiu no Erro
xyzM0 -x→ ?❌ x não está no alfabeto

src/main.cpp

Responsabilidade: não implementa nenhum algoritmo; só chama as etapas em ordem e imprime as tabelas entre elas.

carregarArquivo(caminho, afnd, "variavel");     // ETAPA 1

  • argv[1] permite escolher outro arquivo de entrada. O padrão é exemplos/professor.txt, com exemplos/entrada.txt como alternativa se ele não for encontrado.

  • Cada etapa gera um objeto novo, então dá para imprimir o "antes" e o "depois" de cada uma.

🎯11. Pontos técnicos que o professor pode explorar

Clique em cada pergunta para ver a resposta.

1. Por que getDestinoAFD é lento?

Ele faz uma busca linear em todas as transições, ou seja, O(T) por consulta. Uma matriz tabela[estado][simbolo] daria O(1). Para o tamanho dos exemplos, não faz diferença.

2. O que conta como épsilon?

isEpsilon aceita ε, &, eps, epsilon e também "E". Consequência: uma alternativa formada só pela letra E maiúscula seria interpretada como ε, não como terminal.

3. Por que a palavra e é aceita como variavel?

Porque D2 = {C, M} contém M, que é final. É o comportamento correto: e é uma vogal, e a gramática aceita uma ou mais vogais.

4. Por que inalcançáveis quase nunca aparecem na minimização?

Porque a determinização já parte de {S} e só cria conjuntos alcançáveis (o <Z> do exemplo 3 some ali). A BFS da minimização funciona como garantia formal.

5. O estado inicial pode ser removido?

Não. A condição i != inicial o mantém mesmo que esteja morto, para o AFD continuar tendo um estado inicial válido.

6. O que acontece com um caractere fora do alfabeto?

Ele não passa pelo Erro: getDestinoAFD devolve -1 e a palavra é rejeitada com "sem transição". O resultado é o mesmo (rejeição), só muda a mensagem.

7. Por que o Erro não aparece como morto no relatório?

Porque o VerificarEstados ignora explicitamente o estado de erro (i != estadoErro), já que ele é morto de propósito.
